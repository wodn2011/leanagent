# BUG-001 漏洞与利用分析（/work/test/target · fortune cookie）

> 标准答案 = `/work/0010-2021-30-fortunecookie1/exploit/{poc.py, poc2.py}`。本文先吃透标准答案（几个漏洞、各 primitive、拿 shell 原理），再据此重做 agent（避免再改得过度定制）。

## 一、二进制
- 路径 `/work/test/target`；Fortune Cookie 菜单：`1.eat 2.create 3.edit 4.read 5.exit`，`alarm(0x3c)` 60s 自退。
- 保护：**Full RELRO**（GOT 只读）+ PIE + Canary + NX。
- libc：glibc 2.39（无 `__free_hook`/`__malloc_hook`）。
- BSS 布局：`msg[32]`(@0x4060，8B 指针) | `msg_size[32]`(@0x4160，4B int) | `urandom`@0x41e0 | `cookie_num`@0x41e8。`stdout`/`stdin`/`stderr` 的 FILE* 在 0x4020/0x4030/0x4040。`__dso_handle`@0x4008（指向 PIE 自身）。

## 二、漏洞（2 个不同根因；"int-underflow" 是 OOB 写的 size 子问题，不单列）

### 漏洞 1：OOB signedness mismatch（edit_cookie / read_cookie）— 主漏洞，标准答案用的就是这个
- `scanf("%llu",&idx)` 读 **unsigned** 64-bit，但边界检查 `cmp rdx,cookie_num; jl` 用 **signed** 比较。
- 大 unsigned 值（如 `0xFFFFFFFFFFFFFFF8` = -8 signed）绕过 `jl` → `idx` 越界（负数 → 访问 `msg[]`/`msg_size[]` 之前的 BSS）。
- **read 路径**（read_cookie）：`printf("%s", msg[idx])` → 把 `msg[idx]`（越界读出的指针）当字符串打印 → 越界读 / 泄漏。
- **write 路径**（edit_cookie）：`read(0, msg[idx], msg_size[idx]-1)` → 往 `msg[idx]`（越界读出的指针）指向的地址写 → 越界写。
  - **size 子问题**：`msg_size[idx]` 越界读 4B（别名 `msg[]` 某 entry）；若该 entry=0（未分配）→ `size-1 = 0xFFFFFFFFFFFFFFFF` → glibc `read` 检测 size>`SSIZE_MAX` **返回 -1 不写**。**修复：先 create 一批 cookie 填 `msg[]` 堆指针 → `msg_size[负idx]` 非零可用**（这是 agent 之前一直踩的坑）。

### 漏洞 2：UAF（eat_cookie）— 真实漏洞，但标准答案没用
- `eat_cookie`：`free(msg[idx])` + 把 `msg[cookie_num-1]` swap 进 freed slot，但**不清零 `msg[idx]` 指针** → dangling。
- 之后 `edit_cookie`/`read_cookie` 仍能经 dangling 指针访问 freed chunk → UAF read/write（需 tcache reclaim 才能控地址）。

## 三、每个漏洞的 primitive

| 漏洞 | CRASH | INFO_LEAK | ARB_READ | ARB_WRITE | HEAP_OBJECT_CONTROL | 备注 |
|---|---|---|---|---|---|---|
| OOB signedness | ✓ idx=-1→msg[-1]=0→`printf(%s,0)` segfault | ✓ read_cookie 负idx 泄 libc/PIE | ✓ 读可控地址 | ✓ edit_cookie 负idx 写可控地址 | — | **直接 ARB_WRITE，主路线** |
| UAF | ✓ | ✓ 读 freed chunk | — | 经 tcache 间接 | ✓ tcache reclaim | 需 setup，间接 |

## 四、拿 shell 的利用脚本原理（poc2.py — House of Apple 2 via stderr）

**用漏洞 1 的 ARB_WRITE 伪造 `stderr` 的 `_IO_FILE` 结构 → `exit` 触发 FSOP → `system(" sh")`。**

### 步骤
1. **create 26 个 cookie**（idx 5-30）→ `msg[]` 填堆指针 → 使 `msg_size[-4]`（别名 `msg[30]` 低 4B）非零可用。此时 `msg[-4] = *(0x4040) = stderr` 的 `FILE*`（libc 地址）。
2. **edit_cookie(-4)** → `read(0, stderr_addr, msg_size[-4]-1)` 写到 `stderr` 的 `_IO_FILE` 结构。先写 `_flags`(0xfbad2087)+padding 桥到 `_IO_read_ptr`，让 `printf` 能读到 `_IO_read_ptr`。
3. **read_cookie(-4)** → `printf("%s", stderr)` 泄露 `_IO_read_ptr`（`stderr+0x08`，libc 内指针）→ `libc_base = leaked - 偏移`。
4. **伪造 `stderr` 的 `_IO_FILE`（House of Apple 2，0xe0 字节）via edit(-4)**。关键字段（偏移是 `_IO_FILE` 通用结构偏移）：

| 偏移 | 字段 | 值 | 作用 |
|---|---|---|---|
| 0x00 | `_flags` | `0x00687320`（`" sh\0"` 小端）| `rdi`=stderr 时 `FILE[0:8]=" sh"` → `system(" sh")` |
| 0x08 | `_IO_read_ptr` | `0` | =`wide_data->_IO_write_base`，`_IO_wdoallocbuf` 要求 0 |
| 0x10 | `_IO_read_end` | `1` | =`wide_data->_IO_write_ptr`，`_IO_flush_all` 检查 `write_base<write_ptr` |
| 0x20 | `_IO_write_base` | `0` | =`wide_data->_IO_buf_base`，`_IO_wdoallocbuf` 要求 0 |
| 0x68 | `_chain` | **`system`** | `fake_wide_vtable[0x68]`=`*(stderr+0x68)`（见别名）|
| 0x88 | `_lock` | `stderr+0x40`（可写、不重叠）| lock 获取不崩 |
| 0xa0 | `_wide_data` | **`stderr-0x10`** | ★把 wide_data 字段别名到 stderr 可写区 |
| 0xc0 | `_mode` | `1`（>0）| 触发 wide path |
| 0xd0 | `_wide_vtable`(wide_data+0xe0) | **`stderr`** | ★`fake_wide_vtable=stderr` → `*(stderr+0x68)`=你写的 system |
| 0xd8 | `vtable` | **`_IO_wfile_jumps`** | 过 `IO_validate_vtable` |

5. **`exit(0)` 触发** → `_IO_flush_all_lockp` 遍历 `_IO_list_all` 到 `stderr`：
   - `_flags & 0x8000==0`（0x00687320 ✓）→ 继续
   - `_mode>0`（=1）→ wide path
   - `wide_data->_IO_write_base`(stderr+0x08=0) `<` `wide_data->_IO_write_ptr`(stderr+0x10=1) → 通过
   - `vtable=_IO_wfile_jumps` 过校验 → 调 `vtable[0x18]`=`_IO_wfile_overflow`
   - `_IO_wfile_overflow`：`wide_data->_IO_write_base`(0)==0 → 调 `_IO_wdoallocbuf`
   - `_IO_wdoallocbuf`：`wide_data->_IO_buf_base`(stderr+0x20=0)==0 → 取 `wide_data->_wide_vtable`(stderr+0xd0=stderr) → 调 `*(fake_wide_vtable+0x68)`=`*(stderr+0x68)`=`system`，`rdi`=stderr，`stderr[0:8]=" sh"` → **`system(" sh")` → shell**。

### 三个核心技巧
1. **`_wide_data = FILE - 0x10`**：把 wide_data 的字段（`_IO_write_base`@+0x18、`_IO_write_ptr`@+0x20、`_IO_buf_base`@+0x30、`_wide_vtable`@+0xe0）**别名映射到 FILE 自身可写区**（stderr+0x08/0x10/0x20/0xd0）——伪造 wide_data 不用另找可写内存，全塞在 FILE 结构里。
2. **`_wide_vtable = FILE 自身`**：`fake_wide_vtable=stderr` → `*(fake_wide_vtable+0x68)`=`*(stderr+0x68)`=你写在 `_chain`(0x68) 的 `system`。**一处写两用**（`_chain` 既是字段又是 fake vtable 的 `__doallocate` 槽）。
3. **`_flags = " sh\0"`**：`_IO_wdoallocbuf` 调 vtable 函数时 `rdi=FILE*`，FILE 头 8B=`" sh"` → `system(" sh")` 直接拿 shell，不用找 `/bin/sh` 字符串地址。

## 五、备注
- **poc.py 走 stdout 路线**（leak PIE via `__dso_handle` → 两步写 `msg[0]=puts@GOT` → leak libc → BSS 伪造 `wide_data`/`wide_vtable`（`__doallocate`=system）→ 覆写 stdout）。原理同（House of Apple 2），但 **stderr 路线（poc2.py）更简洁**（单 FILE 结构 + 别名 + `" sh"` trick，无需 BSS 伪造额外结构）。
- 标准 answer 只用**漏洞 1**（OOB signedness → ARB_WRITE → FSOP）。漏洞 2（UAF）未用。
- **agent 之前失败的关键点**：① S3 把 OOB 漏报成只有 CRASH+INFO_LEAK（漏 ARB_READ/ARB_WRITE）→ S4 只验到 INFO_LEAK → S5 没 ARB_WRITE 走不了 fsop；② S4 不知道"先 create 填 msg[] 让 msg_size[负idx] 非零"（size=0→read -1 写不进）→ PoC 写不进 FILE 结构；③ S5 没读 fsop skill → 走错路线（写 __dso_handle 这种不可控目标）；④ S4/S5 用 pwntools `process()`+`recvuntil` → recv/send 死锁 hang 烧墙钟（应该 stdin 管道喂输入）。
