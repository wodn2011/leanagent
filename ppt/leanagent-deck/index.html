五层错误处理：错误向上冒泡，策略向下注入

L0 基础
网络/容器/文件系统 — httpx 重试 · console log 双写兜底 drvfs 吞文件
L1 工具内建
单次调用健壮性 — latin-1 replace 防崩 · isfile 检查 · RLIMIT 4GB · 超时自适应提示
L2 会话内
agent 循环健康 — 无 submit 提醒×5 · 重复守卫>5 拒 · GLM 软超时 600s · 墙钟/预算
L3 契约
交付质量 — schema 字段级反馈×3 · RouteGate 终检（未声明/失败未换线拒）
L4 编排
跨会话策略 — 总结注入新 attempt×8 · 全用尽判负收尾

GLM 流式挂死9 小时 → 600s 软超时自愈

复读循环 25+ 次守卫拒绝+可执行引导

双保险设计：关键约束（skill 路由）在 L2 闸门 + L3 终检各拦一次，绕过任何一层都会被另一层接住。

// takeaways

能力边界与五条方法论

诚实的能力边界（2/32 失败）：0023 需"单次 1/256 概率+外层循环"的概率思维——Agent 生成了正确形态的两段写 payload、验证了全部机制，但困在"单次调到 100%"的确定性执念。闸门保证知识被读，不保证心智模型被切换。0013 无官方解参照，打满预算未突破。

① 契约>提示

输出必须工具化+schema 校验，不靠 prompt 恳求

② 路由>检索

闸门+调用序核对，知识才会被用

③ 总结>长上下文

撞钟压缩记忆复用，不硬撑上下文

④ 终检>劝说

"失败必须换线"写进校验而非 prompt

⑤ 守卫>自律

资源上限+重复检测，不信任模型自觉

Agent 工程的本质不是让 LLM 更聪明，
而是把"应该做"变成"不做就干不了"。
